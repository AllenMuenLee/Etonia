# Etonia account, billing and AI backend

This directory is deployable code, not a provisioned Supabase project. Create a
project before following the deployment steps. Local notes work without a backend;
paid AI and purchases fail closed until account services are configured.

## Privacy boundary

The database stores account IDs, product IDs, verified subscription status and
expiry/history, encrypted purchase locators, renewal credit grants, numeric AI usage,
and random per-install device IDs (generated by the app, never hardware IDs).
Email and sign-in sessions are managed by Supabase Auth. Session credentials on
the device use Keychain/secure storage; `subscription.json` retains only the
preferred model. Existing local credits and debug grants are not imported.

There are no note, PDF, chat, prompt, response, image or embedding tables, and no
Storage buckets. An AI request forwards the **current prompt, recent conversation
text, and selected PNG crop** to a provider in memory. Optional drawing coordinates
contain only page dimensions and crop bounds. The full note image is never
serialized. Responses are returned to the device and never persisted.
Request bodies, provider responses, purchase tokens and errors are not logged.
Do not enable body capture in a gateway, tracing agent or monitoring integration.
OpenAI calls explicitly use `store: false`; provider-side retention is governed
by the provider account's own settings and terms, not by this Supabase code.

## Create and configure the project

1. Create a Supabase project in your chosen region. Keep `billing_private` out of
   the exposed API schemas. Do not create document Storage buckets for this feature.
2. Enable the **Google** authentication provider in Supabase Auth (configure the
   OAuth client IDs matching `dart_defines.json` and the client secret in
   `supabase/.env.local`). Email OTP and Apple sign-in are not used.
   Also enable **Anonymous sign-ins** and **Manual linking** (Auth > Sign In /
   Providers; `config.toml` sets both for local runs). A device that has not
   signed in with Google gets an anonymous account on the free plan, and the
   device's ID is remembered. Google sign-in later links Google to that same
   account. Anonymous accounts can only read their status: they cannot verify
   purchases or use AI. Consider enabling CAPTCHA to limit anonymous sign-ups.
   `billing_private.account_plans` lists every account with its plan, `free`
   included. A Google-signed-in free account gets a one-time $0.50 AI credit
   (`plans.one_time_credit`). The credit is granted once per account and once
   per device, never to anonymous accounts, and it never refills. It pays for
   Haiku, Luna, Sonnet and Sol only, and is used only while no paid plan is active. `billing_private.devices` lists every device and its last account.
3. Copy `config/backend.example.json` to ignored `dart_defines.json`, set the HTTPS
   project URL and `sb_publishable_...` key. Preserve any unrelated existing public
   app configuration. Remove AI provider secrets from app build configuration.
   Neither a service-role key nor an AI provider key belongs in Flutter defines.
4. Copy `supabase/secrets.example` to `supabase/.env.local` and fill server secrets
   locally or in the dashboard. The runtime supplies `SUPABASE_URL` and
   `SUPABASE_SERVICE_ROLE_KEY`; do not add those to Flutter configuration.
5. Set `AI_MODEL_CONFIG` to a single-line JSON object based on
   `model-config.example.json`. Replace every placeholder with an available model
   in your provider account and confirm its rates. Sample rates mirror the old
   app configuration, **not a claim about current provider pricing**. Rates are
   integer micro-USD per 1,000 tokens: $2/million tokens means `2000`.
   Model routing, rates, output limits and allowed aliases are server-controlled.
   Two optional fields per model cut the cost of a request:
   - `reasoningEffort` (`none`, `minimal`, `low`, `medium`, `high`): sent as
     OpenAI's `reasoning_effort` or Gemini's `thinkingLevel`. Reasoning is
     billed as output, usually the largest part of a request; `low` is a good
     start for tutoring. Leave it out for a model that does not reason (or for
     Claude, which ignores it), or the provider rejects the request.
   - `cachedInputMicroPerKilo`: the provider's price for cached input. The
     fixed instructions and answer schema (several thousand tokens) are the
     same on every request, so providers serve them from cache; without this
     field, users are billed full price for them.
6. Generate `PURCHASE_TOKEN_ENCRYPTION_KEY` from 32 cryptographically random bytes
   and base64-encode them. Back it up securely. Rotating it requires re-encrypting
   existing locators; changing it alone makes old subscriptions unreadable.

### Apple

Set the App Store Connect In-App Purchase private key, key/issuer IDs, numeric
app ID, and actual bundle ID. The current native bundle ID is `com.etonia.app`.
Download Apple root certificates from Apple's PKI page and put their base64 DER
contents into the `APPLE_ROOT_CERTS_BASE64` JSON array. Signature verification
includes the certificate chain, online revocation checks, bundle and environment.
Set the App Store Server Notifications V2 URL to:

`https://YOUR_PROJECT_REF.supabase.co/functions/v1/store-events`

Create the subscription products from the migration (or update both the product
mapping and app IAP product-ID defines to match your actual store products).
Use a separate Supabase project with `APPLE_ENVIRONMENT=Sandbox` for testing;
production never falls back to sandbox. Enable In-App Purchase and Keychain
Sharing in the app's signing configuration. The checked-in entitlements include
the app-specific keychain access group.

### Google Play

Enable the Android Publisher API and authorize a service account for this app's
subscription/order access in Play Console. Put its JSON key in server secrets.
Configure real-time developer notifications through a Pub/Sub **authenticated
push** subscription. Use the same `store-events` URL, set its exact audience and
push service account email in secrets, and permit the Pub/Sub service agent to
mint the service account's OIDC tokens. The handler verifies the Google JWT,
issuer, audience, verified email and package before processing notifications.
For a test project only, set `ALLOW_GOOGLE_TEST_PURCHASES=true`.

Both stores receive the Supabase user UUID at purchase time. The server requires
the matching `appAccountToken` / `obfuscatedExternalAccountId`. A receipt belonging
to another account cannot be claimed. Existing purchases created before account
binding need a separately audited administrator migration; there is deliberately
no "first person to restore owns it" path.

## Deploy

From the repository root, after filling the project and secrets:

```powershell
npx supabase login
npx supabase link --project-ref YOUR_PROJECT_REF
npx supabase db push
npx supabase secrets set --env-file supabase/.env.local --project-ref YOUR_PROJECT_REF
npx supabase functions deploy billing --project-ref YOUR_PROJECT_REF
npx supabase functions deploy ai --project-ref YOUR_PROJECT_REF
npx supabase functions deploy store-events --project-ref YOUR_PROJECT_REF
flutter run --dart-define-from-file=dart_defines.json
```

`verify_jwt=false` is intentional: `billing` and `ai` verify the bearer token with
Supabase Auth themselves. `ai` and purchase verification reject anonymous users;
`billing` status accepts them, but only to record the device and return the free plan. `store-events` verifies
Apple signed payloads or Google OIDC tokens. No endpoint accepts a caller-supplied
user ID or balance. All database mutation RPCs are service-role only; client roles
cannot execute them or read the private tables. UI status is returned by `billing`.

## Accounting and failure behavior

- Store status is rechecked on billing refresh and before AI access. Signed store
  notifications also update renewals/refunds while the app is closed. If verification
  is unavailable, paid access fails closed. App resume and expiry refresh the UI.
- A unique store transaction grants one allowance. Replaying a restore or webhook
  never refills it. Canceled auto-renewal preserves access through paid expiry;
  revocation, hold and expiry remove access. Grace periods follow verified stores.
- When several subscriptions are active, the highest plan wins, then latest expiry.
  Credits belong to that subscription's current transaction and do not roll over.
- A database transaction locks the account and reserves its metered balance before
  calling the provider. The output budget is constrained by credits and configured
  prices, with conservative input/image allowance. Each request holds only its own
  worst-case cost, so up to four requests per account may be in flight at once
  (a pending request stops counting toward that after ten minutes). Usage settlement is idempotent, and an old request cannot refund into
  a new renewal's allowance. Charges are capped at the reserved balance.
- Unlimited models use no credits but still have output, concurrency and rate
  limits: 30 API calls/minute and 300 AI requests/24 hours per account. These are
  abuse limits in addition to store entitlements, and can be adjusted in migration
  follow-ups. Configure provider/project spending limits as an additional cap.
- A definitively rejected provider call releases its reservation. A timeout,
  missing usage report or failed settlement leaves it pending, holding its credits. **Do not automatically refund or retry an uncertain
  provider call.** It may already have incurred cost. Monitor pending requests
  older than two minutes in `billing_private.requests`; after checking provider
  billing, an administrator can settle using `public.ai_settle(user_id, request_id,
  cost_micro_usd, input_tokens, output_tokens, false)` or explicitly release it
  with zero values and `true`. No content is stored for replay.
- AI currently returns a complete response after accounting; it does not stream
  partial tokens. Up to 100 recent messages (bounded to 128,000 UTF-8 bytes) are
  sent as provider context with each request.

## Validation

```powershell
flutter analyze
flutter test test/features/payment test/features/editor/backend_ai_client_test.dart
npx --yes deno check --config supabase/functions/deno.json supabase/functions/ai/index.ts supabase/functions/billing/index.ts supabase/functions/store-events/index.ts
npx --yes deno test --allow-read --allow-env --config supabase/functions/deno.json supabase/tests
```

SQL tests execute the real migration in embedded PostgreSQL (PGlite), including
role permissions, account ownership, replay, revocation, expiry, reservations and
renewal settlement. Before release, exercise real sandbox purchase, restore,
renewal/refund notifications and sign-in on both platforms against the deployed
project. Local tests cannot verify store credentials, SMTP or signing profiles.
